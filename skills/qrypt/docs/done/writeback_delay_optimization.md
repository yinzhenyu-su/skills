# 写入回写延时（Writeback Delay）优化方案

### 现状分析：`time.Sleep` 的原生缺陷

目前在 `internal/vfs/writeback.go` 的 `Write` 函数中，系统通过如下方式处理同步触发：

```go
go func() {
    time.Sleep(100 * time.Millisecond)
    fs.enqueueSync(node)
}()
```

**这种实现存在两个严重问题：**

1. **写放大与协程爆炸**：如果一个大型文件被分 1000 次微小写入（如 `cp` 操作），系统会瞬间启动 1000 个协程。100ms 后，这 1000 个协程会几乎同时竞争 `node.mu` 并调用 `enqueueSync`，造成严重的 CPU 峰值和锁竞争。
2. **逻辑不确定性**：100ms 是硬编码的魔法值，它无法感知写入是否真的结束，也无法防止在极短时间内的重复无效同步。

---

### 改进方案：基于节点的 Debounce（防抖）计时器

为了提升高频写入场景下的系统稳定性，建议将简单的 `Sleep` 改为文件节点级别的防抖计时器。

#### 核心逻辑设计

1. **计时器绑定节点**：在 `node` 结构体中增加 `syncTimer *time.Timer` 字段。
2. **写入时“重置”**：
    * 每当 `Write` 发生时，首先检查 `node.syncTimer`。
    * 如果计时器正在运行，调用 `Stop()` 废弃掉之前的同步意图。
    * 重新创建一个 200ms（或可配置）后触发的 `time.AfterFunc` 计时器。
3. **效果**：无论 `Write` 被调用多少次，只要相邻两次写入的间隔小于 200ms，系统就永远只会在最后一次写入结束后触发 **一次** 真正的上传任务。

#### 配合 `Release` 实现极速响应

- **场景**：用户保存文件并关闭编辑器。
* **优化**：在 `Release`（文件句柄关闭）调用时，主动检查 `syncTimer`。如果存在，立即 `Stop()` 计时器并 **同步执行一次 `enqueueSync`**。
* **价值**：这保证了“随关随传”，用户关闭文件后不需要再额外等待防抖时间，同步任务会立刻进入队列。

### 总结

通过 **防抖计时器** 替代 `time.Sleep`，可以将系统从“无脑并发”转变为“智能攒批”，显著降低大批量文件写入时的系统负载，并解决 FUSE 线程在高压力下的响应延迟。
