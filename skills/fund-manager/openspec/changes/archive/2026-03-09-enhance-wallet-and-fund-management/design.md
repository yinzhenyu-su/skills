## Context

系统目前已有基础的 CRUD 和抓取能力。接下来的挑战是将这些离散的功能串联起来，形成更自动化的工作流（如交易时的自动发现）和更高维度的汇总（如钱包级别的分析）。

## Goals / Non-Goals

**Goals:**
- 实现钱包级别的汇总分析逻辑。
- 实现 `buy` 命令的基金自动发现机制。
- 优化 CLI 参数结构，提高命令的灵活性（指定钱包）。
- 提供全局基金列表查看。

**Non-Goals:**
- 不涉及数据库 Schema 的破坏性变更。
- 不提供跨钱包的全局汇总（仅限单钱包内汇总）。

## Decisions

### 1. 钱包汇总算法
- **Decision**: 在 `wallet list` 时，为每个钱包执行一次 `get_holdings` 逻辑。
- **Rationale**: 这样可以复用已有的盈亏计算代码，确保数据定义的一致性。

### 2. 基金自动发现逻辑
- **Decision**: 只有当输入符合 6 位数字且数据库中不存在该代码时，才尝试进行抓取。
- **Rationale**: 防止无效输入导致多余的网络请求和错误的基金创建。

### 3. CLI 参数注入
- **Decision**: 将 `--wallet` 参数作为可选参数添加到 `Buy` 和 `Sell` 变体中。
- **Rationale**: `clap` 的扁平化设计可以方便地解析这种覆盖逻辑。

## Risks / Trade-offs

- **[Risk] 性能问题** → **Mitigation**: 如果用户有很多钱包，`wallet list` 会发起多次数据库查询。当前数据量下 SQLite 性能完全足够，后续可考虑增加本地缓存。
- **[Risk] 自动抓取失败** → **Mitigation**: 如果基金不存在且抓取失败，应清晰地提示用户“无法获取该基金信息，请手动添加或检查代码”。
