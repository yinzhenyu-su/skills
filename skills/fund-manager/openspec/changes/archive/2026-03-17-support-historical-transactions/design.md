## Context

目前系统的交易日期通过 `get_today()` 硬编码为系统当前日期。这导致用户无法补录历史持仓，且测试环境被迫与真实时间耦合。

## Goals / Non-Goals

**Goals:**
- 在 `buy`, `sell`, `import` 命令中引入可选日期支持。
- `import` 命令的 CSV 格式应支持每行可选的日期列。
- 使交易日期成为结算状态逻辑（`pending` vs `settled`）的驱动因素。

**Non-Goals:**
- 不支持 YYYY-MM-DD 以外的日期格式（如带时间的 ISO8601）。
- 不支持交易日期的自动时区转换。

## Decisions

### 1. 命令行参数接口
- **选择**: 在 `src/cli.rs` 的相关子命令中增加 `#[arg(long)] date: Option<String>`。
- **理由**: `--date` 是补录操作的事实标准命名。

### 2. CSV 解析策略
- **选择**: CSV 解析器检查列数。如果存在第三列，则尝试解析为日期；否则使用全局指定的日期或默认“今日”。
- **理由**: 兼容旧的（2列）CSV 格式，同时赋予高级用户单行录入的能力。

### 3. 结算逻辑重构
- **选择**: 将原有的 `today` 变量替换为 `transaction_date`。
- **逻辑**: `if is_nav_available_at(transaction_date) { settled } else { pending }`。
- **理由**: 核心逻辑保持一致，只是将参考点从“系统现在”移动到了“业务发生时”。

### 4. 日期合法性校验
- **选择**: 使用 `chrono` 的 `NaiveDate::parse_from_str` 进行严格校验。
- **理由**: 防止用户输入如 `2024-02-30` 或 `invalid-date` 导致数据库记录混乱。

## Risks / Trade-offs

- **[风险] 份额不足校验逻辑复杂化** → **[缓解]** 在补录历史 `sell` 交易时，系统仍仅根据“当前总份额”进行简单拦截。更复杂的流水对账（如在 2023 年卖出但在 2024 年买入导致的负份额）在本阶段暂不处理。
- **[风险] 历史净值缺失** → **[缓解]** 记录为 `pending`。用户需要运行 `fund sync` 或后续增强 `fetch_at_date` 来结算这些历史记录。
