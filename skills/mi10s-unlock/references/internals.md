# 原理与边界

## 1. 为什么没有"免解锁 Root"

Android 的信任链是：BootROM → ABL/Bootloader → `boot` 分区 → dm-verity/SELinux。解锁 BL 是这条链上唯一"由用户决定"的开关，绕开它就只能靠内核漏洞在内存里提权。对本机（小米 10S，HyperOS 1.0，Android 13，补丁级 2024-03）而言：

| 条件 | 实际情况 | 后果 |
|---|---|---|
| Build 类型 | `ro.debuggable=0`，user 版 | 没有 `adb root` |
| dm-verity | `enforcing` | 系统分区改一个字节就起不来 |
| SELinux | `enforcing` | 即使拿到 uid 0 也受策略约束 |
| 内核 | `4.19.157-perf`，2024-06 编译 | 已含 2024 年之前的公开 LPE 修复 |
| 公开利用链 | 无针对该 build 的可用 PoC | 只能自己挖，成本远超收益 |

结论：**要么解 BL，要么放弃 root**，没有第三条路。

## 2. 网上那些"免解锁"说法

| 说法 | 核实 |
|---|---|
| B 站/知乎"免 BL 临时 root、一键提权" | 内核 LPE 工具，靠个人站/网盘分发、无源码。对 2024-03 补丁级的 4.19 内核无可用链；且临时 root 一旦写持久分区就变砖（AVB 校验不过，官方渠道救不回） |
| "KernelSU 越狱模式免解 BL" | KernelSU 官方（v3.x）无此功能，仍要刷改过的 boot；该说法出自 AI 生成文章 |
| InfinityCore / CVE-2026-98260 "有小米利用链" | 该文档只针对 Linux 7.0 / Galaxy S26，与 4.19 内核无关 |
| 9008/EDL 免授权降级回 MIUI | SM8250 有泄露的签名 firehose，物理上能刷；但 2025-09 起澎湃 1.0 机型封堵，且**降级 ≠ root**，之后仍要走官方解锁 |
| 第三方"免解锁 root"付费服务 | 大多是把"你本来就能解锁"或"临时提权"包装成服务；部分需要远程控制你的机器 |

## 3. 绑定绕过利用了什么

HyperOS 给解锁加了一道"社区资格"门槛（5 级 + 实名 + 答题）。这道门在**绑定账号**这一步校验，而校验依据来自客户端上报的字段。小米 Settings 里有三个缺陷叠加：

1. **logcat 泄露完整请求**
   `com.android.settings.bootloader.CloudDeviceStatus` 把绑定请求整包打到日志：
   ```
   D/CloudDeviceStatus: args: <base64(AES)>
   I/CloudDeviceStatus: headers: <base64(AES)>
   ```
   `args` 是请求体，`headers` 里含 `serviceToken`（会话 Cookie）。任何能跑 adb 的进程都能读。

2. **密钥硬编码在 APK 里**
   ```
   AES-128-CBC  key = "20nr1aobv2xi8ax4"   iv = "0102030405060708"
   HMAC-SHA1    key = "10f29ff413c89c8de02349cb3eb9a5f5" + 同串
   ```
   所谓加密只是混淆；签名密钥就是服务端唯一认的凭证。

3. **服务端信任客户端自报的 `rom_version`**
   请求体里的 `rom_version` 决定走哪套风控：
   - `V816.*`（澎湃）→ 新政策 → 无资格直接 `30001`
   - `V14.*`（MIUI）→ 旧政策 → 绑定后等 168 小时

   所以只需一行替换：`V816 → V14`，再用泄露的密钥重新签名，服务端就按 MIUI 的设备处理。

另外实测该接口的 `nonce` **不防重放**（手机自己发一次失败后，同一份报文从电脑重放仍可成功），这也是它能work的前提之一。

> 小米后续的修补方向正是第 1、3 点：服务端改成按设备记录资格（`30001` 强制校验），新 ROM 移除该日志。

## 4. 绑定成功 ≠ 解锁成功

绑定只是第一道门。解锁时走 `/api/v3/ahaUnlock`，服务端还会判：设备激活时长、账号地区、账号风控、以及是否仍要社区授权（`30002`）。所以 `bind-bypass.py` 返回 `code 0` 之后，**必须**再跑一次 `miunlock` 看真实判定。

## 5. 等待期怎么算

官方口径是 168 小时，但实测落到的是**设备激活时间**这条规则（`10013: 设备激活不足 7 天`）。一台已经用了很久的老机器，绑定后往往能立刻解锁——所以别默认"必须等 7 天"，先跑一次 `miunlock`：

- 返回 `20036` → 真的没到期，按 `notice` 等
- 直接返回 `encryptData` 并 `Unlock successful` → 省了 7 天

`20036` 不消耗额度；只有真正取到 `encryptData` 才占用"每月一次"（`20030`），而 `encryptData` 本身在重启后即失效。

## 6. 为什么必须用密码/浏览器登录

`unlockApi` 是高危服务。免密/扫码登录拿到的会话跳转票据是：

```
/sts?...&ticket=0&pwd=0
```

`pwd=0` 表示本次会话没走过密码校验，`/sts` 会直接 `401`。换成账号+密码+短信的浏览器登录后 `pwd` 才有效。这在 MiUnlockTool 的 issue 里也是高频坑（#135 / #142 / #144）。

## 7. 风险与红线

- **只能对你自己拥有的设备操作。**
- 解锁会**清空全部数据**，且不可逆；先备份。
- 账号层面的风控是真实存在的：用非官方手段高频操作可能被限制（`20033`），恢复手段有限。
- 锁着 BL 去写持久分区 = 变砖，且官方渠道因 AVB 失败无法恢复。任何"临时 root"工具都不要碰系统分区。
- 保留对应版本的官方线刷包，这是唯一的兜底。
- 解锁后 TEE/Play Integrity 相关能力受损，银行/钱包类 App 可能不可用；这是状态性的，不是 bug。
