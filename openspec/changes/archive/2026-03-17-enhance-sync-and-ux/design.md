## Context

`fund-manager` 需要更强大的数据维护能力。随着“历史交易”功能的引入，同步命令必须能够补全过去缺失的净值数据。同时，作为 CLI 工具，良好的帮助文档是提升用户留存的关键。

## Goals / Non-Goals

**Goals:**
- 实现基于日期区间的批量净值抓取。
- 实现智能补全：自动发现数据库中缺失的净值日期。
- 重构帮助信息，增加使用示例。

**Non-Goals:**
- 不涉及实时行情同步（依然以收盘净值为准）。
- 不涉及复杂的图形化进度条库（保持轻量级，使用简单的字符反馈）。

## Decisions

### 1. Provider 接口扩展
- **选择**: 在 `Provider` trait 中增加 `fetch_range` 方法。
- **理由**: 使批量获取成为一级公民，避免循环调用单日接口导致的效率低下和触发反爬。

### 2. 同步模块化
- **选择**: 创建 `src/sync.rs` 模块。
- **理由**: 将原本臃肿的 `main.rs` 中的同步与结算逻辑解耦，便于单元测试。

### 3. 智能补全算法
- **逻辑**: 
    1. 获取所有 `pending` 交易的最早日期 $D_{min}$。
    2. 获取数据库中各基金最新记录后的断档区间。
    3. 调用 `lsjz` API，设置 `startDate = min(D_{min}, Gap_{start})`。

### 4. CLI 帮助文本增强
- **策略**: 使用 `clap` 的属性宏。
    - `#[command(help_template = "...")]` 自定义展示风格。
    - 在各 `Commands` 枚举成员上增加 `long_about` 以包含 `EXAMPLES` 部分。

## Risks / Trade-offs

- **[风险] 批量同步数据量过大** → **[缓解]** 设置默认分页限制（如 20 天），并在 CLI 提示中告知用户。
- **[风险] 帮助信息过长** → **[缓解]** 区分 `fund --help`（简短）和 `fund buy --help`（详细）。
