## Context

qrypt 的删除与修改能力已具备基础实现，但行为契约分散在 VFS、driver、cache 三层，且异常分支（上传失败、重启恢复、删除后残留 pending）缺少统一约束。近期已确认修改上传链路需要 hash 上报闭环才能稳定完成，因此有必要将该行为提升为明确设计决策，并补齐删除与写回的一致性边界。

约束条件：

- 保持现有 write-back 架构，不引入在线流式上传模型。
- 保持 rclone 兼容的加密格式（文件头 + 分块加密）。
- 优先最小改动，避免重构已有可用主流程。

## Goals / Non-Goals

**Goals:**

- 定义删除操作在本地与远端的一致性流程，避免“远端已删、本地仍重试上传”的状态冲突。
- 定义修改上传的稳定闭环，明确 hash 上报、finish 条件与 commit/finish 回退路径。
- 定义恢复策略，仅恢复有效 pending 任务并在失败时可重试、可观测。
- 建立覆盖关键路径的验证矩阵，确保删除和修改在常见编辑器行为下可预期。

**Non-Goals:**

- 不引入新的存储后端或消息队列。
- 不实现远端原地 patch（仍采用整文件重加密上传）。
- 不改变现有 CLI 参数或用户交互模型。

## Decisions

### 1) 删除采用“远端成功后本地收敛”策略

- 方案：Unlink/Rmdir 调用远端 Delete 成功后，再清理本地节点、dirty chunk、pending 记录和内存缓存映射。
- 原因：以远端状态为真源，避免本地先删导致回滚复杂。
- 备选：本地先删再异步删远端。放弃原因：失败补偿复杂，容易产生幽灵文件。

### 2) 修改上传采用“hash 闭环优先，commit 兜底”策略

- 方案：分片上传完成后先计算加密对象 MD5/SHA1 并调用 update/hash；若 finish=true 直接完成；否则再走 OSS commit + upload/finish。
- 原因：已验证此路径可避免 callback 203 场景并与现有实现兼容。
- 备选：始终强制 commit。放弃原因：在 callback 故障下成功率较低。

### 3) 恢复仅处理可判定有效的 pending 项

- 方案：挂载恢复时先校验 pending 关联节点与必要元数据；非法或孤儿记录直接清理并记录告警。
- 原因：避免无效重试挤占队列，降低恢复抖动。
- 备选：无条件全部重试。放弃原因：会放大历史脏数据问题。

### 4) 失败重试与可观测性最小增强

- 方案：保留现有重试框架，补充关键状态日志（删除收敛、hash finish、commit fallback、pending 清理）。
- 原因：便于验证与排障，且改动面小。
- 备选：引入复杂状态机存储。放弃原因：超出本次范围。

## Risks / Trade-offs

- [Risk] 删除时本地清理不完整导致残留缓存 → Mitigation: 统一清理入口，按 fid/path 双索引清理。
- [Risk] hash 计算增加 CPU 开销 → Mitigation: 复用现有加密分块读取流程，避免重复 I/O。
- [Risk] 多编辑器触发语义差异（Flush/Release/Truncate） → Mitigation: 在验证矩阵中覆盖典型写入序列并补齐缺失钩子。
- [Trade-off] 继续采用整文件重传会增加带宽消耗，但实现稳定性和兼容性更高。
